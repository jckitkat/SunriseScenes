## What this is, in one paragraph

Sunrise Scenes is a desktop app (Electron, plain JavaScript) for drawing Project Sunrise
missions as stacks of sentence-shaped nodes and saving them as the Lua scripts the mod loads.
Project Sunrise is an offline preservation mod for Destiny 2; a mission is a Lua chunk that
returns a table of handlers. The editor's design follows Evan Moran's GDC talk "Walking,
Talking and Projectiles: Storytelling Tools in Destiny 2" (scenes as tabs, sentence nodes,
orthogonal lines, no state in the nodes). The author, jckitkat, is scripting the Red War
campaign with it, starting with Homecoming (`mission_towerfall`).

## Setting up on Linux

```bash
git clone https://github.com/jckitkat/SunriseScenes.git
cd SunriseScenes
npm ci
npm test
npm run smoke
npm start
```

Node 22 or newer. README.md, "Linux", covers the three things that bite: missing libraries
(`libnss3`, `libnspr4`), the Electron sandbox on Ubuntu 24.04+, and pointing the app at the
game folder. What has been verified on Linux: unit tests (35), the smoke run from source and
from a packaged build, all on Ubuntu 26.04 arm64 inside WSL. What has not: a real Linux
desktop session, an x64 Linux build, and a real Proton or Wine game folder.

The game itself is a Windows program. On Linux it will run through Steam's Proton or Wine,
and the Sunrise folder is `<game>/bin/x64/Sunrise` inside that. The mod is a replacement
`steam_api64.dll` in `<game>/bin/x64/`. Nobody on this project has run Sunrise on Linux yet.

## How the app is put together

docs/ARCHITECTURE.md has the detail. The short version:

- **Layer 1, pure logic** (runs in Node, unit-tested): `src/catalog.js` (node types as
  sentence templates), `src/state.js` (the document and every edit to it), `src/compile/`
  (one compiler per mode), `src/sdk.js` (reads a generated SDK module), the two importers,
  `src/lualint.js`.
- **Layer 2, the page**: `src/ui/` and `src/main.js`.
- **Layer 3, disk**: `electron/files.cjs` only, reached through `electron/preload.cjs`.

Four modes: free scene (`lib.flow`), campaign (`lib.campaign` table), **mission** (our own
runtime in `src/compile/mission.js`: a Flow tab of legs and steps plus one tab per scene),
freeroam (`lib.freeroam` + `content.lua`). Mission mode is the one in active use.

A saved mission is two files side by side in the scripts folder: `<name>.lua` (generated,
marked "Generated by Sunrise Scenes") and `<name>.scene.json` (the drawing). The drawing is
the source; the Lua is rebuilt from it on every save.

## What happened in the last working session (2026-10-06), newest last

1. Authored scenes would not play. Cause found in Sunrise's source: `activate{}` only starts a
   scene; `activate{spawn = true}` also prepares its cast. The "Start scene" node got three
   settings: start (with cast), start bare, stop.
2. Scenes still did nothing. They wait on **event gates**. Sunrise 0.5.1's SDK did not list a
   scene's event keys; the unreleased `master` does. Sunrise was built from source and the
   SDK regenerated; every scene row gained `event_keys = { 0x…, … }`.
3. Added the "Send event N to scene" node (`scene:send_event{key}`), reading `event_keys`.
4. Added to Sunrise's debug UI a scene detail panel with Send buttons (the fork's branch).
5. Added highlight / copy / cut / paste / group move to the editor.
6. One scene (`scene_cayde_golden_gun`) played by hand but never from the script. After
   several wrong theories (timing, cast preparation), a byte trace added to Sunrise showed
   the script was sending different events from the ones pressed by hand: the panel showed a
   gate **ordinal** column and an index column, the editor numbers by index, and "1 and 3"
   (ordinals) were positions 3 and 5. The author was told to use events 3 and 5. **Whether
   that then played from the script was not reported back.** Ask.
7. Linux support, this document, and the git work.

Lessons worth keeping from item 6: Sunrise's `sunrise.log` and the byte trace settle in one
run what guessing did not settle in six. When a script and a manual action differ, compare
what was actually sent before theorising. And "unmapped target, N B" in Sunrise's event view
is the label of every incident packet, not an error.

## What is known about scenes (the hard-won part)

docs/SUNRISE.md, "Authored scenes", is the full record. The essentials:

- `context:scene(id):activate{}` starts a scene; `activate{spawn = true}` first places the
  cast squads in reserve and binds their actor controls. Both put the same bytes on the wire
  for the scene itself.
- A scene's graph has gates. `scene:send_event{key = 0x…}` adds one key to the running
  generation. Keys accumulate; re-sending one changes nothing; a new start clears them.
- The SDK lists a scene's keys in gate order as `event_keys`. The editor's event number is
  the 1-based position in that list. Each gate also has an ordinal (-1 "opens every scene"),
  not printed in the Lua SDK, visible only in the debug panel.
- Every scene's list begins with `0x385838EC`. What it does is unknown; the Cayde scene
  played without it and was not harmed by it.
- A scene the host refuses is silent to the script (not a Lua error). It shows in the log as
  `result=scene_refused` with a status name.
- A scene started before the client has entered the area did not play (seen once).

## Sunrise itself: building, logging, the local changes

- Source: `stanuwu/Sunrise`. Builds on Windows with Visual Studio 2026 Build Tools:
  `msbuild Sunrise.sln /m /p:Configuration=Release /p:Platform=x64`, giving
  `build/x64/Release/steam_api64.dll`. Upstream's README has a Linux cross-build with
  `clang`, `cmake`, `ninja` and `xwin`; that has not been tried here. `CMakeLists.txt` globs
  the sources, so the files added on the fork's branch need no CMake change.
- Install: copy the DLL over `<game>/bin/x64/steam_api64.dll` with the game closed. Keep the
  release DLL as a backup. The launcher records the installed DLL's hash in
  `<game>/.sunrise/install-state.json` and may offer to "repair" a self-built one.
- Logging: in `<game>/bin/x64/Sunrise/settings.json`, `core.logging.file_sink: true` and
  `core.logging.levels.server: "info"`. The log is `<game>/bin/x64/Sunrise/logs/sunrise.log`.
  At `info` it grows quickly; the old machine was left with it **on**.
- The fork's `scene-debug-tools` branch adds, all under `Sunrise/src/server/`:
  `ui/activity_host/activity_host_sdk_scene_details.{h,cpp}` (the panel),
  `signal_authored_scene` / `stop_authored_scene` in `activity/activity_sdk_mission_runtime`,
  and `activity/host_runtime_scene_trace.h` with calls in three `host_runtime*.cpp` files
  (lines `ev=scene_auth stage=encode|transport|cancel … body=<hex>`).
  Caveats: not clang-formatted; the trace's `source=` field is only right on `encode` lines
  (transport and cancel always say `panel`); the first install of the panel build hung the
  game once at launch, never reproduced and never investigated.
- Useful source files when a script misbehaves:
  `server/activity/mission/mission_script_lua_*_api.cpp` (what each Lua call accepts),
  `server/activity/mission/mission_script_runtime_dispatch.cpp` (how an intent is delivered
  or refused), `server/activity/activity_sdk_mission_prepare.cpp` (why a scene is refused),
  `client/content/activity/activity_sdk_lua_missions.cpp` (what the Lua SDK prints).
- Upstream PR 128 (Strange Terrain strike support) was looked at and is unrelated to scenes.

## The Homecoming script

`mission_towerfall/` in the missions fork's branch:

- `mission_towerfall.scene.json` + `mission_towerfall.lua`: the Mission-mode version. Flow:
  one cutscene, leg "underwatch", steps home / gear / find. Scene tabs include `cast`,
  `first_contact`, `post_gun`, `cayde` (the author has rearranged them since the first
  translation; trust the file, not this list).
- `mission_towerfall.campaign.lua.bak` and `.campaign.scene.json.bak`: the author's earlier
  campaign-mode version. Kept because it exists nowhere else.
- The scenario key is `MISSION_TOWERFALL`; its SDK module is
  `sdk/lua/missions/mission_towerfall_80b500bc.lua` in an install. The SDK is generated by
  the game from its own data on first launch and is **not** in any repository; a new install
  has to generate it (with a Sunrise build newer than 0.5.1, or `event_keys` will be missing
  and "Send event" nodes will report an error).

## Ways of working that the author responded well or badly to

These are observations from the session, not rules the author stated.

- They test in the game quickly and report briefly. Ask for one specific observation at a
  time, and say exactly where to look.
- They were told three timing theories in a row that turned out wrong, and said so curtly.
  Check a theory against the evidence in hand before presenting it; say plainly when a
  conclusion is a guess.
- They prefer the editor to behave like Bungie's tool where there is a choice, and chose the
  scenes-as-tabs design over their own first idea when the comparison was laid out.
- A form-based editor was rejected as clunky; everything is on the canvas now.
